# 问题1调查报告（inv-send-large 子代理，2026-11-16）

## 0. 发送链路总览
```
Inputbar.tsx (sendMessage) → messageThunk.sendMessage → addMessage(用户消息+stub助手消息)
  → getTopicQueue(topicId).add(fetchAndProcessAssistantResponseImpl)
  → ensureKernelTopic → extractTextFromUserMessage（只取触发消息自身文本）+ extractImagesFromUserMessage（图片预算≤950KB/图）
  → kernelChat.sendToKernel → pendingStubs.set + rememberPendingUser(FIFO)
  → window.api.dshTopicSend (preload/index.ts:264-301, ipcRenderer.invoke)
  → main kernel/index.ts:619-804 Dsh_TopicSend handler（白名单重建 cleanOptions，逐字段校验，非法 throw）
  → topics.ts:1266 sendMessage（能力缝登记→mountedState 漂移判定→admitEncodedImages→createUserMessage→agent.send(message,'next-turn',true) 即返回）
  → 内核异步跑回合：dsh-agent-loop ReactLoopAgent.step() 每 step 用 session.deriveMessages() 全量历史 buildRequest → dsh-llm-pi-ai → provider
  → session/event 逐条广播（kernel/index.ts:313-336）→ renderer handleSessionEvent 投影 → turn/end → finishTurn 收口
```
关键结构事实：渲染层只上行触发消息本身，不上行历史；历史由内核从 session log 派生。IPC payload 与对话规模基本无关（图片除外，有预算）。

## R1（最可能）：内核请求端没有任何上下文治理——每步全量历史进请求，超限即 provider 拒绝 → 当轮终局
- 规模相关性：严格单调。唯一随对话规模持续增长的失败面。
- `.pnpm/@deepseek-ai+dsh-agent-loop_f64f522e6c47e067f272158f26294e4c/.../lib/index.js:613`：
  ```js
  const { request, preparedCall } = await this.buildRequest(turn, step, assembly.tools, system, this.session.deriveMessages(), signal);
  ```
  每个 step（含工具循环内每一步）都用全量派生历史组请求，循环内无截断/压缩。
- fork 侧 src/main/kernel/topics.ts:462 只挂了 `agent/request` waterfall（仅覆盖 reasoningEffort，`attachReasoningEffortListener` L460-481）；全仓 grep `agent/request-error`、`spill`、`output-retention` 在 fork 代码与 dsh-agent/dsh-agent-loop 内部均零命中——没有 spill/spill-policy/retention，没有请求端预算。
- 溢出的归宿：`.pnpm/@deepseek-ai+dsh-llm-pi-ai@.../lib/index.js:1286-1294`（mapStopReason）：`isContextOverflow(message, contextWindow)` 或 `isContextWindowExceededError(message.errorMessage)` → `failure.code = CONTEXT_WINDOW_EXCEEDED`。前提是 provider 报错文本能被识别；识别不了落到普通 error。CONTEXT_WINDOW 不在 dsh-llm 默认可重试码内，agent-loop L653-662 `if (action?.kind !== "retry") throw new LlmError(...)`——无自动重试，一次拒绝 = 当轮 error。
- 结构缺口：渲染层已有上下文预算概念——src/renderer/src/services/TokenService.ts:186-206 `estimateHistoryTokens` 用 `takeRight(msgs, maxContextCount)` 窗口化（输入框百分比用），settings.ts 的 assistant `contextCount` 存在——但这个预算从不随发送上行（sendToKernel options 无 context 字段，kernel 也无处消费）。UI 展示的预算是假的。
- 为什么表现为"偶发"：只有当历史+系统提示+工具面逼近 provider 窗口时才触发；不同 provider 报错文案不同识别率不同；工具轮内每步都重发全量历史。
- 修复建议（符合 CLAUDE.md §7.9）：请求端上下文选择无公共缝可及（deriveMessages 在 loop 内部，agent/request waterfall 只触配置）——与 thinkingReplay 同一先例。做法：在现有 patches/@deepseek-ai__dsh-llm-pi-ai@0.1.1-rc.2.patch 上加第三个中性 globalThis 门（复用 src/main/kernel/thinkingReplay.ts:149 的 fail-safe 门模式），按 fork 侧预算（token 窗口 + 回合边界完整 + 用户消息保留）裁剪请求消息；预算经 topics.ts 发送参数登记（公共缝，与 reasoningEffort 同模式）。同时渲染层发送前用 estimateHistoryTokens 做前置检查，超预算给 toast 引导开新话题。

## R2（次之）：同话题队列 concurrency: Infinity + pendingStubs 单槽 + finishTurn 无条件删 stub → 多路并发回合互踩，stub 卡 PENDING = 输入锁死
- src/renderer/src/utils/queue.ts（getTopicQueue）：`new PQueue(options)` 调用点不传 concurrency → 默认 Infinity；messageThunk.ts 的 dispatchMultiModelResponses 每 mention `queue.add(impl)` 到同一话题队列 → 多个 impl 并发执行。
- src/renderer/src/services/kernelChat.ts:493：`pendingStubs.set(topicId, assistantMessageId)`——Map 单槽，后发覆盖先发。
- kernelChat.ts:628-630（startTurn）：
  ```ts
  const stubId = pendingStubs.get(topicId)
  if (stubId === undefined) return
  ```
  静默返回，无日志——被踩的回合 turn/start 时 stub 已被覆盖/删除，投影完全丢失。
- kernelChat.ts:1321-1322（finishTurn 收尾）：`streams.delete(topicId); pendingStubs.delete(topicId)`——无条件删，先结束的回合会把还在跑的下一回合的 stub 删掉；后续该话题所有 turn/start 全部走 630 静默返回 → 那条助手消息永久 PENDING、零块。
- PENDING 无限挂 → useMessageOperations.ts:775-788（messageIds.some(... PENDING||PROCESSING)）恒真 → InputbarCore.tsx:191 `isSendDisabled = noContent || searching || (isLoading && !queueWhileLoading)` → 输入与发送键永久锁死（直到重载话题）。
- 追问泵（followupQueue.ts:21 pumpFollowupQueue 在 finishTurn 之后跑，kernelChat.ts:615-620）顺序安全。
- 修复建议：① getTopicQueue 默认 `concurrency: 1`（发送本来就是回合制）；② startTurn:630 的静默 return 加 logger.error + 给 stub 消息落 ERROR 块（孤儿回合可见化）；③ 若确需并发多模型，stub 键应带回合身份（如 Map<topicId, Set<msgId>> 按 turn/start 配对），删 stub 须核对身份。

## R3（第三）：mountedState 漂移 → 发送热路径内 dispose + 整会话 resume，O(n) 事件重放
- src/main/kernel/topics.ts:1340-1353（sendMessage 内）：每次发送都 computeMcpSignature/computeTurnRegSignature 比对；漂移即 `await handle.dispose()+liveHandles.delete`，随后 openTopic→ensureAgent(1702-1919) 走 resumeOrCreateSession（1901）→ 从 SQLite 重放全部事件。会话越大重放越慢。
- MCP 抖动放大器：computeMcpSignature(357) 对 listTools 失败计 'unreachable'——服务不可达期间签名不变；服务恢复瞬间签名改变 → 恰好在下一次发送时触发整会话重挂。发送 IPC 长时间 pending；若 resume 中途失败，sessionResumeFallback.ts fail-closed throw（可见，OK）。
- 相关：forkTopic(797-854) 重发/重新生成把 events.slice(0,turnStartIndex) 整段前缀复制成新会话（ctx.agents.create({seed})）——大话题重发 = O(n) 事件写入。内核行为，fork 不可改。
- 修复建议：把"非运行中话题的漂移重挂"移出发送热路径——发送时若 isTopicRunning 沿用旧活体（1715 已有先例），漂移登记成待重挂，由后台（回合边界后）执行 dispose+resume；MCP 'unreachable'→恢复的签名跳变属预期，可对 unreachable→reachable 的转换豁免立即重挂（下一轮再挂）。

## R4（第四）：渲染层 O(n) 热路径 + 逐事件广播无背压 → 大话题上 UI 饱和
- useMessageOperations.ts:775-788 useTopicGenerating：每次 store 变更全话题 messageIds.some(...)，无 memo selector。
- kernelChat.ts:1310（finishTurn→setTopicFulfilled）：`store.getState().assistants.assistants.flatMap(...)` 每回合结束全量 flatMap。
- src/main/kernel/index.ts:313-336（registerEventForwarding）：每个 session/event 逐窗口 webContents.send，无合并/背压（flushBlockUpdate 已有 >500ms rAF 延迟 warn 取证，L803-807）。
- 后果是卡顿与感知失败，不是数据失败。
- 修复建议：useTopicGenerating 换 memoized selector（按 topicId 切片）；setTopicFulfilled 的行查找走 memoized 根投影选择器；broadcast 在 fork 侧按 rAF 合并 chunk 类事件。

## R5（第五）：巨型单条消息（默认不转文件）跨 IPC 与进内核日志
- src/renderer/src/settings.ts:280 `pasteLongTextAsFile` 默认 false（threshold 1500，L281）→ 超长粘贴保持纯文本进发送链。
- IPC 层：electron 41.2.1；invoke 走 Structured Clone，无文档化硬性大小上限。preload 与 handler 均无大小限制。
- 已检查图片路径有界：kernelImages.ts:18 MAX_ENCODED_BYTES=950*1024、L20 MAX_LONG_EDGE=2048，策略表压不进 → `data:''` → L175-177 throw（可见失败）；单图 base64 ≤~1.3MB。
- 修复建议：把 pasteLongTextAsFile 默认改 true 或超阈值时 toast 提示。

## R6（伴随缺陷，静默失败点，违反 CLAUDE.md §10，单独列出）
1. src/renderer/src/store/thunk/messageThunk.ts:417-419：`triggeringUserMessage` 找不到 → 仅 logger.error('kernelChat: triggering user message not found, skipping send')——不建错误块、不置 ERROR、不清 loading（外层 try 正常走完，catch 的 finally 在内层 try 432-451 里）→ stub 永久 PENDING + loading 永久 true，双门锁死且无可见错误。
2. src/renderer/src/pages/home/Inputbar/Inputbar.tsx:289-292：附件上传失败仅 logger.warn('Failed to send message:')，无 toast；setText('') 已在 283 清空输入——用户内容凭空消失。
3. src/main/services/MessagesService.ts:262（checkRateLimit）：`const topicId = assistant.topics[0].id` 用第一个话题而非当前话题——限流窗口读错话题。
4. kernelChat.ts:1215-1222（finishTurn state undefined 分支）：只 pendingUserIds.delete+endTurn+return，不清 loading、不删 pendingStubs——孤儿回合的部分收口（与 R2 叠加时加剧锁死）。

## 3. 结论
发送失败随规模增长的第一根因是 R1：请求端零上下文治理（dsh-agent-loop lib/index.js:613 每 step 全量 deriveMessages()，fork 无预算、无 spill、无重试；渲染层的 contextCount 预算从不随发送上行）——单调、必然、错误虽可见但用户感知为"发送不成功"。第二梯队是 R2 的 stub 互踩静默锁死与 R3 的发送热路径内 O(n) 重挂。IPC/preload/handler/补丁/投影各层均已排除大小相关缺陷。
