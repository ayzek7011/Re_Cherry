# 问题2调查报告（inv-files 子代理，2026-11-16）

## 生命周期事实
- 上传入口 `FileManager.uploadFile`（src/renderer/src/services/FileManager.ts:94-109）→ IPC `File_Upload` → 主进程 `FileStorage.uploadFile`（src/main/services/FileStorage.ts:306-345），落盘名 = `uuid + ext`（uuidv4），目录 = `{userData}/Data/Files`（src/main/utils/file.ts:199）。
- 索引行在 Dexie `files` 表（src/renderer/src/databases/index.ts，`files: EntityTable<FileMetadata, 'id'>`）。
- 关键点：Dexie 行不存可用物理路径——展示/定位时由 renderer 用 `filesPath + '/' + file.id + file.ext` 现场重建（FileManager.ts:126-129），`filesPath` 来自 Redux `runtime.filesPath`。
- 定位/打开 = FilesPage 点击 → `window.api.file.openPath(重建路径)` → 主进程 `shell.openPath`（FileStorage.ts:927-932）。删除 = 先删行后删字节（FileManager.ts:156-165）。备份 = BackupManager 打包 `{userData}/IndexedDB + Local Storage + Data/`，还原在下次启动换目录（src/main/services/BackupManager.ts）。

## 候选 1（最可能）：runtime.filesPath 启动竞态 + mini 窗口永远为空
- src/renderer/src/store/runtime.ts:74 — `filesPath: ''`（初值空）；src/renderer/src/store/index.ts:123 — persist `blacklist` 含 `'runtime'`（不持久化，每次启动都从 '' 开始）。
- src/renderer/src/hooks/useAppInit.ts:187-193 — 唯一赋值点，一次性、无 catch、无重试：
  ```ts
  void window.api.getAppInfo().then((info) => {
    dispatch(setFilesPath(info.filesPath))
    dispatch(setResourcesPath(info.resourcesPath))
  })
  ```
- `useAppInit()` 只在 src/renderer/src/components/TopView/index.tsx:43 调用（主窗口）。mini 窗口（src/renderer/src/windows/mini/**）grep `getAppInfo|setFilesPath|useAppInit` = 0 命中；store/index.ts:141 `syncList: ['assistants/', 'settings/', 'llm/', 'note/']` 不含 runtime，storeSync 也不会把 filesPath 带进 mini 窗口。mini 窗口的 filesPath 是 '' 直到永远，而 mini chat 复用 `@renderer/pages/home/Messages/MessageContent`（src/renderer/src/windows/mini/chat/components/Message.tsx:3）。
- 消费点全部同步读它：FileManager.ts:127-128 / 236-237；图片块 src/renderer/src/pages/home/Messages/Blocks/ImageBlock.tsx:26：
  ```ts
  : [`file://${FileManager.getFilePath(block?.file)}`]
  ```
  且 ImageBlock 是 `React.memo`（:76）不订阅 runtime.filesPath——启动窗口期内渲染的图块在 filesPath 到位后不会重渲染，坏 URL 挂到重挂载为止。
- 偶发性机理：主窗口里 IPC 往返约几百 ms 就到位，用户操作通常更晚 → 大多数时候正常。坏的时刻：① 开机头几秒内点定位/看图；② mini 窗口 100% 失败；③ 启动窗口期内渲染的 memo 图块持续坏；④ 该 promise 一旦 reject（任何瞬时 IPC 故障）无重试、无可见信号，整个会话 filesPath='' 全坏。
- 修复建议：① filesPath 变成 FileManager 模块级缓存，renderer 入口最早处（entryPoint/init）`await window.api.getAppInfo()` 首帧前完成，失败重试 + warn 取证 + 用户可见提示；② 或 FileManager.getFilePath/getFileUrl 改为经主进程 `FileStorage.getFilePathById`（FileStorage.ts:1915-1917 已有同逻辑）异步解析；③ ImageBlock/FileList/paintingFileUrl 用 `useAppSelector(s => s.runtime.filesPath)` 订阅；④ mini 窗口 entryPoint 补 `getAppInfo` 调用。

## 候选 2（直接命中"定位/打开失败却毫无反馈"）：FilesPage 定位点击无 catch → 静默吞错

- 图片预览 FileList.tsx:96 `src={FileManager.getFileUrl(file)}` 无 onError：坏 URL 时组件依赖 onLoad 才去掉 opacity:0 → 永远转圈，静默消失。
- 仓库内已有正确范本：src/renderer/src/components/ClickableFilePath.tsx:37-39 / 62-64 —— catch 后 `toast.error('chat.input.tools.open_file_error')`。
- 修复建议：click 处 .catch → toast.error（带文件名与原因）；ImageViewer 加 onError → 占位符；定位失败时给出"文件可能已被移动/删除"类显式动作，绝不静默、绝不自动删。

## 候选 3：ext 丢点 —— 绘画 base64 图的定位/删除链路坏 + 孤儿字节
- src/main/services/FileStorage.ts:728（saveBase64Image 返回值）与 :839（savePastedImage）：
  ```ts
  ext: ext.slice(1),   // 'png'，丢了点
  ```
  而盘上文件名是 `uuid + '.png'`（:719 writeFile，destPath = uuid+ext 带点）。所有路径重建假设 ext 带点：FileManager.ts:127 `filesPath + '/' + file.id + file.ext` → `uuidpng`（没点）→ 定位必失败；`window.api.file.base64File(file.id + file.ext)`（kernelImages.ts:126）同样读不到。
- 消费链（当前唯一入口）：src/renderer/src/pages/paintings/model/runPainting.ts:44-45 → metadata 不进 db.files，只存进 painting 记录。后果：① `paintingFileUrl.getPaintingFilePath`（src/renderer/src/pages/paintings/utils/paintingFileUrl.ts:16-18 → FileManager.getFilePath）另存/外部打开全坏；② 删除 src/renderer/src/pages/paintings/hooks/usePaintingList.ts:107-109 → `FileManager.deleteFiles(files)` → `deleteFile` 行不存在 → false → 每次删 base64 绘画都弹 "N deleted, M failed"（FileManager.ts:172-194 partial_failed toast），字节从未被删 → Data/Files 孤儿累积。
- 偶发性机理：只影响 base64 生成图/粘贴图；普通上传文件 ext 带点（FileStorage.ts:316）。
- 修复建议：主进程把 ext 不变量统一为"带点"，写盘名与 metadata 同源（一处生成，禁止 slice）；一次性迁移修复存量无点行（重建路径时若 `id+ext` 不存在而 `id+'.'+ext` 存在 → 用后者并写回行）；deleteFile 必须核实删除结果并如实返回 Promise<boolean>。

## 候选 4：备份/还原与 Data/Files 的一致性缺口
- backup()（BackupManager.ts 248-355）在应用运行中直接拷贝 LevelDB 的 IndexedDB 目录（无 checkpoint/quiesce）：renderer 正在写 Dexie 时拷贝会漏提交 → 还原后近期 files 行丢失。自动备份只 defer 消息流式（BackupService.ts:472 检查 `state.messages.loadingByTopic`），不管上传中，且可在启动后 1 秒就跑。
- skipBackupFile=true（用户开关，src/renderer/src/pages/settings/DataSettings/BasicDataSettings.tsx:479）时归档里 Data 目录是空壳（:309/:416），restoreDirect:682 `if (dataExists && dataFiles.length > 0)` → Data 不参与还原 → IndexedDB 回滚到旧快照而 Data/Files 保持现状：备份后删过的文件行复活（定位失败）、备份后新增的文件字节变孤儿。
- handleStartupRestore（144-216）逐目录顺序换（IndexedDB → Local Storage → Data）：Data 换失败（Windows 文件锁/AV）时继续启动，只有 logger.error，.restore 留待下次，无用户可见信号——启动后 = 新 Dexie + 旧字节，行列错位。
- 修复建议：还原必须带 Data（归档缺 Data → 拒绝或明确告知后果）；目录 swap 失败 → 阻断启动并给出可见错误（或强提示后重试）；备份前对 IndexedDB 做一致性处理并暂停 renderer 写入；还原结果（成功/失败/部分失败）在 UI 可见。

## 候选 5：findDuplicateFile 返回破损 metadata → 孤儿字节"复活"成坏行
- src/main/services/FileStorage.ts:231-241（match 分支，`file` 是盘上条目名 `"uuid.png"`）：
  ```ts
  origin_name: file,        // uuid 名，不是用户原名
  name: file + ext,         // "uuid.png" + ".png" = "uuid.png.png"
  count: 2
  ```
- 触发链：行已删但字节还在 → 用户再上传同内容 → uploadFile 命中 duplicate 分支返回此坏 metadata → FileManager.uploadFile（:94-109）发现 `db.files.get(id)` 不存在 → `db.files.add(uploadFile)` 落库坏行 → 文件列表出现"名字是 uuid、双扩展名、count=2"的怪行，FileList 预览用 file.name → 永远转圈。
- 修复建议：duplicate 分支返回真实 origin_name（上传文件原名）与 `name: id + ext`；renderer 不为 duplicate 返回值凭空建行。

## 候选 6：引用计数漂移 → 删一条消息把另一条消息的图删掉
- kernelImages.ts:198/237 `db.files.put(file)`（幂等 upsert，不增 count）——同一附件/同内容生成图（确定性 id：attachmentId / sha256，:186/:208-214）被多条消息引用时行 count 仍是 1；删除消息时 messageThunk.ts:176 `Promise.all(files.map((file) => FileManager.deleteFile(file.id, false)))` → count 1 → 行+字节全删 → 另一条消息的图变"找不到"。
- 修复建议：put 前若行存在 → count+1（与 addFile 语义一致）；或删除字节前先扫描 messageBlocks 是否仍引用该 id；"引用不可知时不删"。

## 候选 7：deleteFile 先删行后删字节 + 主进程静默 void
- FileManager.ts:156-165：`await db.files.delete(id)` 之后才 `window.api.file.delete(id + file.ext)`；字节删除失败 → logger.warn → return false——行已不可恢复，调用方（FileAction.ts:56）无从回滚。
- 主进程 FileStorage.ts:369-374：
  ```ts
  public deleteFile = async (_, id) => {
    if (!fs.existsSync(path.join(this.storageDir, id))) { return }
    await fs.promises.unlink(path.join(this.storageDir, id))
  }
  ```
  不存在 → 静默 return；Windows 下 unlink 被 AV/占用（EBUSY/EPERM）偶发拒绝 → renderer false + 孤儿字节。
- 修复建议：先删字节（失败即停，行不删，乐观行回滚 + toast.error）；主进程 deleteFile 返回 Promise<boolean> 并对"不存在"如实回报；批量删除保持 "N succeeded / M failed" 真实信号。

## 总评与修复顺序
单一"偶发找不到"不存在唯一元凶——是四类结构性缺陷叠加：路径重建依赖非持久化且可能为空的 filesPath（候选1）、定位失败全静默（候选2）、metadata ext 不变量被两处破坏（候选3）、备份/还原与删除链路的行列一致性缺口（候选4/5/6/7）。修复顺序建议：候选1+2（用户可见性）→ 候选3（数据修复+不变量）→ 候选7（删除事务语义）→ 候选4（备份还原）→ 候选5/6（计数与去重）。
